# Endless Realm — Tech Stack Proposal

**Audience:** Chief of Staff, Karyu, ER Gameplay Engineer  
**Date:** 23 Nov 2026 (Europe/Vienna)  
**Status: Accepted (Karyu, 2026-11-23)** for options 2b and 3a (character ownership). Device-key identity, per-lobby accounts, and “no central account for v0.1” remain **Proposed — pending Karyu.**

**Constraints:** Godot **4.7.2-stable** (4.8 is still beta) plus matching export templates. Client in **typed GDScript** (Godot 4 C# cannot export to web; Android C# is experimental). Targets: Windows / Linux / macOS + Android; no iOS; web export is a nice-to-have. No official servers for now; solo is offline (in-process sim, no network, no tracking); multiplayer is player-hosted lobbies (host-set max player count, default 50). The authoritative sim is the Godot game itself (listen server or `--headless` dedicated host), not a Go gameplay server. Portal opener sets that instance’s level multiplier on the v0.1 grid (M100 50–150 in steps of 5, i.e. 0.50–1.50 step 0.05; see `docs/design/vision.md` and the stack multiplier decision), locked at open, within a host-set allowed range that always includes 1.00. No level cap; endless gear tiers; everything except cosmetics is farmable; no paid cosmetics at first playable. For v0.1, Android is join-only; desktop or `--headless` hosts come first.

## Decisions

Confirmed by Karyu, 2026-11-23:

1. **Client:** Godot 4.7.2-stable, typed GDScript, matching export templates. Web export is a nice-to-have (locks WebSocket/WebRTC in, and keeps us off Godot C#).
2. **Server language:** **Option 2b, accepted.** The authoritative sim is Godot: a listen server inside the host’s client, or the same export run `--headless`. Solo and hosted play share one GDScript sim. The earlier Go gameplay-server pick is superseded; Go remains a reference / test harness and is reserved for optional later services (see [Amendment 2026-11-23](#amendment-2026-11-23-player-hosted-lobbies)).
3. **Characters:** **Option 3a, accepted.** Characters live on the lobby that created them and can be imported if the other host allows it. Imports, including solo / offline characters, carry `played_offline`, and the host may allow or refuse them. **Identity (Proposed — pending Karyu):** an engineering / Chief of Staff proposal is a device-held key pair (e.g. Ed25519) that identifies the player, with accounts per lobby and the host binding a character to that public key, and no email / password or central account for v0.1. Karyu asked what an account service would cost and how email / password browser games handle it; that identity choice is not decided. Alternative 3b (a central signing / account service) stays open. Host saves under 3a are local (e.g. SQLite or files). PostgreSQL as an official store is not needed for v0.1 while there are no official servers.
4. **Level multiplier:** 0.50–1.50 for v0.1, as **M100 50–150 in steps of 5** (0.50–1.50 step 0.05), **locked once the portal opens**. Source: `docs/design/vision.md` (merged with [PR #1](https://github.com/Karyu42/endless-realm/pull/1)) and this stack decision. The host sets an allowed range on that grid that always includes **1.00** (M100 100). A portal outside that range is rejected with `MULTIPLIER_NOT_ALLOWED` (an additive `proto/v1` change; see the amendment).
5. **Hosting:** No official servers for now. Solo is offline. Multiplayer is player-hosted lobbies. Official-server budget stays deferred. First playable is no longer “local Docker Compose plus a later VM.” v0.1 discovery is LAN broadcast plus join by code/link or direct IP (directory and relay deferred). For v0.1, Android is **join-only**; desktop or `--headless` hosts come first.
6. **Paid cosmetics:** none at first playable.

**Also decided by Karyu, 2026-11-23** (relayed by Chief of Staff):

- Multiplayer = player-hosted lobbies. The host sets the max player count, **default 50**. Karyu, via Chief of Staff: “solo and player lobbies, let players decide on a max player count, defaulted to 50.”
- A lobby browser shows the level multiplier of open portals. If more than 5 portals are open, show at least the 2 lowest and the 2 highest.
- Enemy scaling is dynamic by players in range and uses the **peak** count during an encounter (it does not drop when players leave). Only enemy **max HP** scales; the curve is integer math; loot is personal and unscaled. Spec and numbers: `docs/design/vision.md` **§3.5**, **§6.1 rules 5 / 6 / 6a**, and **Appendix A** in [PR #17](https://github.com/Karyu42/endless-realm/pull/17) (**pending PR #17**; those sections are not on `main` yet). This doc does not copy the numbers. The host implements the curve and uses the Appendix A golden values as tests, once #17 has merged.
- Offline-played characters are flagged. Lobbies can refuse them.
- **Discovery v0.1:** LAN broadcast discovery plus join by code/link or direct IP. The host tries UPnP port mapping; otherwise the host forwards the port manually. A directory service (Cloudflare Workers free tier, €0, ~$5/mo if outgrown) and relay / NAT punch are deferred.

**Engineering / design (not Karyu’s words; pending the load test):** the lobby max and instance cap have a hard ceiling of **1–50**, from the Game Designer’s [PR #17](https://github.com/Karyu42/endless-realm/pull/17) (**pending PR #17**). The host-set max and the default of 50 are Karyu’s (“solo and player lobbies, let players decide on a max player count, defaulted to 50.”); only the 1–50 ceiling is engineering / design, to be confirmed by the 50-bot load test. Until #17 merges, merged `vision.md` still states a party cap of 8.

**Proposed — pending Karyu** (engineering / Chief of Staff; he asked about account-service cost and how email / password browser games work):

- A device-held key pair (e.g. Ed25519) identifies the player; accounts exist per lobby; the host binds a character to that public key. No email / password and no central account for v0.1. Alternative 3b (central signing / account service) remains open.

**Considered (settled, except identity):** Rust as a server language (density vs. sim-code reuse — Godot host accepted instead); C# / .NET (rejected — fights web export and Android maturity); Discord/Google OAuth at first playable (defer); a paid cosmetic / Prism currency surface at first playable (defer, later-phase in PR #1); picking a paid host/VM now (official servers are deferred; a Cloudflare Workers directory remains an option if the deferred directory is taken up); option 3b, still open pending Karyu.

**Engineers can decide (unless Karyu objects):** tick 20 Hz and the units/angle table below; protocol v1 handshake; WebSocket + Protobuf (`godobuf` on the client and the host); JSON `data/` pack; `GameSession` / `WorldSource` client shape; GUT 9.7.1 CI shape; PCG32 + golden-fixture pattern tests; the anti-cheat basics below. Host-local saves (e.g. SQLite or files) are the v0.1 store under 3a; in-process instance rooms remain the starting point and live in the Godot host.

Characters brought from elsewhere, including offline / solo ones, are **imports** carrying a `played_offline` flag. A host setting allows or refuses imports. With no official authority, a client-side flag is not tamper-proof; enforcement is the host owning its own saves.
- **Allowed multiplier range:** the host sets a range on the v0.1 **M100 grid** (50–150 hundredths in steps of 5, i.e. 0.50–1.50 step 0.05; source: `docs/design/vision.md` / this stack decision) that always includes **1.00** (M100 100). - **Hosting / local dev:** Docker Compose PostgreSQL is no longer needed under 3a. Note as a follow-up; do not change compose in this PR.

Intended committed output is `client/src/protocol/v1/` (mirroring `server/internal/protocol/v1/` for Go). Regeneration is `make proto`. Drift is checked by `proto-codegen-check`. ## Agree first (client + server)

Lock these before implementation. A connect **version handshake** disconnects on mismatch with a clear error; breaking wire changes bump the protocol version.

| Item | Agreement |
|---|---|
| Protocol version | `u16` in the first message both ways; current = `1`. **`proto/v1` is the source of truth.** Additive changes (new fields and enum values, no renumbering) keep version 1; a breaking change bumps it. See the amendment for owning PRs. |
| Tick rate | **20 Hz** (50 ms) authority. Same rate for client input sampling, `LocalSim`, and the host sim. Client **renders at display rate**. |
| World units | Sim and wire: `float` **1.0 = one tile**. Client constant **`TILE_PX = 16`** (16 px source art) defined in one place; art scale is not restated elsewhere. |
| Axes / angles | **Godot 2D convention on the wire and in the sim**, including the host and the Go reference harness — **no sign flips.** +X = 0 rad, **+Y down**, positive angle = **clockwise on screen**. |
| Time | Sim events and pattern spawns use **tick index** (`u32`), not milliseconds. |
| Numeric precision | **float64** for all sim math (GDScript floats are 64-bit). **float32 only on the wire.** |

## Headline stack

- **Client:** Godot 4.7.2-stable, typed GDScript, matching export templates. Autoload `GameSession` owns a `WorldSource`: `LocalSim` (offline, in-process, steps at 20 Hz — this is **solo**) and `NetClient` (input frames out; snapshots/events in; prediction + reconciliation for self; interpolation buffers for others). Gameplay/render nodes only read entity state and emit input intents; they interpolate between 20 Hz ticks, and evaluate bullets analytically at render time. Sim (movement, pattern evaluation, damage, loot, XP) lives in plain `RefCounted` classes, not Nodes. Tests: **GUT 9.7.1**; CI runs `godot --headless --import` first and fails if tests did not actually run. For v0.1, Android is a join client only.
- **Host:** the same Godot export, either as a **listen server** inside the host’s client or run `--headless` as a dedicated host. It runs the same `LocalSim` / rules classes authoritatively and speaks the existing wire protocol. The listen-server host’s own player sends `InputIntent`s into the sim on the same path as remote players (zero latency, no special-case code). **Do not use Godot’s high-level MultiplayerAPI for game state** (no RPCs). Transport may use `WebSocketPeer` / `TCPServer` or `WebSocketMultiplayerPeer` as a socket only. v0.1 hosts are desktop or `--headless` (Karyu’s default of 50; recommended for big lobbies). Android listen-hosting is **post-v0.1**. The in-repo Go gameplay server remains the current implementation until host work lands, then becomes a reference / test harness; `server/` keeps building, and its required checks stay required until replaced (see the amendment).
- **Transport:** WebSocket first (desktop + Android + web). Leave a transport interface so desktop can add UDP/QUIC later. Do not use raw ENet as the only path (no web).
- **Wire:** Protobuf. Client and host codec: **godobuf**, the same generated GDScript, committed under `client/src/protocol/v1/` once `make proto` emits it, checked by `proto-codegen-check` (today that job covers only the Go output in `server/internal/protocol/v1/`). Shared *game data* (items, enemies, patterns, XP) is versioned JSON in `data/`, loaded by the Godot sim and by the Go harness — not compiled shared code. `proto/v1` stays the source of truth. The transport and framing stay the same; additive `proto/v1` changes are listed in the amendment (PR #12 for portal messages and M validation; a future host-lobby protocol PR for `MULTIPLIER_NOT_ALLOWED` and the handshake).
- **Tick / netcode:** 20 Hz authoritative sim. Client sends `(move, aim, fire_held, seq)` each tick. Bullets are deterministic **closed-form** patterns — the host broadcasts pattern *spawns*, not per-bullet state. Hits, loot, and XP are authority-only (the host).
- **Instances:** Opening a portal creates an instance and **locks** the opener’s level multiplier, which must lie in the host’s allowed range on the M100 grid 50–150 step 5 (always includes 1.00; otherwise `MULTIPLIER_NOT_ALLOWED`). The instance cap is the lobby’s max players (host-set, default 50). A hard ceiling of 1–50 is engineering / design, **pending PR #17** and **to be confirmed by the load test**. The lobby browser shows open portals’ multipliers as decided above.
- **Accounts / persistence (3a, accepted for ownership):** character saves live on the lobby that created them (e.g. SQLite or files). Imports, including solo / offline characters, carry `played_offline`; the host may allow or refuse them. **Identity (Proposed — pending Karyu):** a device-held key pair (e.g. Ed25519), accounts per lobby, host binds a character to that public key; no email / password or central account for v0.1.

Golden fixtures become regression tests (the Go harness may still run them).

## Transport, protocol, shared data

**Pick:** WebSocket + Protobuf. Godot 4 has `WebSocketPeer` on desktop, Android, and web (and can listen with `TCPServer` or `WebSocketMultiplayerPeer` as transport only). Schema in `proto/`; **`proto/v1` is the source of truth.** The Godot client and host share one **godobuf** GDScript codec generated from the same `.proto` files (intended path `client/src/protocol/v1/`; Go structs stay in `server/internal/protocol/v1/`). Regeneration is `make proto`. `proto-codegen-check` fails if `make proto` would change committed output; today it covers only the Go files, and will cover the GDScript files once godobuf is wired into `make proto`. godobuf v0.7.0 is documented for Godot 4.6 — if it cannot cover 4.7.2 or a needed feature, fall back to a hand-written, fixture-tested encoder. Round-trip fixtures must encode/decode identically.

The **transport and framing stay the same**. Additive `proto/v1` changes (new fields and enum values, no renumbering; version stays 1 unless a change breaks compatibility):

- Lobby / portal messages and M validation, including `INVALID_MULTIPLIER`: [PR #12](https://github.com/Karyu42/endless-realm/pull/12).
- `MULTIPLIER_NOT_ALLOWED`, and public-key handshake fields (`Hello` pubkey + signed challenge; **Proposed**, pending the identity decision): a future host-lobby protocol PR from the Server Engineer.

**Considered:** a small hand-written binary codec if godobuf is a poor fit for 4.7.2 (still fixture-tested) — this is the fallback above; WebRTC data channels (UDP-like, NAT traversal, works on web, more ops); QUIC/UDP for desktop + WebSocket fallback (later, not a start). Raw ENet/UDP is not the only transport (no web export); fine as a later desktop path. Godot MultiplayerAPI RPCs are not used for game state.

**Shared data:** items, enemies, bullet patterns, loot tables, and the XP curve live in versioned JSON under `data/` with a JSON Schema. The Godot sim and the Go harness load the same files. No shared compiled library in v1. YAML is an alt if designers prefer it; JSON is easier to validate in CI.

## Tick rate, netcode, bandwidth, hit validation

- Fixed **20 Hz** authority. Client **renders at display rate**. `LocalSim` also steps at 20 Hz (solo and the host). Render nodes interpolate between ticks; bullets are **evaluated analytically at render time**. Alt: 30 Hz authority if instances stay tiny and melee needs to feel snappier — engineer can try 20 and bump.
- Client samples input at the sim tick, stamped with `seq`. The host is authoritative for positions, damage, loot, XP. The listen-server host’s own player sends that input through the same `InputIntent` path into the sim as remote players, with zero latency and no special-case code, so solo, host, and remote all exercise one path.
- **Own movement:** prediction + reconciliation against authority snapshots.
- **Others:** interpolate from `NetClient` buffers (~100 ms interpolation delay).
- **Projectiles:** never replicate each bullet. The authority emits `PatternSpawn { id, pattern_id, seed, spawn_tick, origin, params, source_id }`. Positions are a **closed-form** `f(spawn_tick, t, params)`, not integrated frame-by-frame. Both sides use **PCG32** with a **fixed seeding rule** — not Godot `RandomNumberGenerator` and not Go `math/rand`. Shared **golden-fixture tests:** the same pattern JSON + seed must yield the same positions at tick N within an epsilon (regression tests on the GDScript sim; the Go harness may keep a copy). Client is visual; **only the authority applies hits**.
- **Hit validation:** the authority tests collisions with **swept or sub-stepped** checks **between ticks** so fast bullets cannot tunnel through a player. Use a short **position history** (≈100–200 ms rewind) so latency does not make grazing impossible. Reject hits that miss the pattern math, ignore client-reported damage, cap input rate, and sanity-check speed/teleports against move stats. No trust of client loot or XP.
- **Interest:** a portal instance is a small room — broadcast the instance. A lobby at the default cap of 50, or a crowded nexus/hub, should use area-of-interest if it grows past a handful of players.

**Bandwidth (order of magnitude):** inputs ≈ 20–30 bytes × 20 Hz ≈ 0.5 KB/s up. Down: ~N players × ~32 bytes/tick plus occasional pattern spawns (not bullet streams). An 8-player instance is a few KB/s; a 50-player lobby is still modest if bullets stay closed-form. Per-bullet replication would explode in a bullet-hell.

## Instances, portals, level multiplier

**Pick:** Hub (nexus) + instanced dungeons, now inside a **player-hosted lobby** (no official servers). The lobby’s max player count is host-set, default **50**, and that value is the **instance cap** (it replaces the old fixed party cap of 8 once [PR #17](https://github.com/Karyu42/endless-realm/pull/17) merges — **pending PR #17**; merged `vision.md` still says 8). A hard ceiling of **1–50** is engineering / design (PR #17), **to be confirmed by the load test**. Karyu’s default of 50 applies to desktop / `--headless` hosts, which come first in v0.1 and are recommended for big lobbies. Android listen-hosting is **post-v0.1**.

1. Player requests `OpenPortal` with a level multiplier. The value must lie on the v0.1 **M100 grid** (50–150 hundredths in steps of 5, i.e. 0.50–1.50 step 0.05; source: `docs/design/vision.md` / this stack decision) and in the host’s **allowed range**, which always includes **1.00** (M100 100). Off-grid values are rejected with `INVALID_MULTIPLIER` ([PR #12](https://github.com/Karyu42/endless-realm/pull/12)). A value outside the host’s range is rejected with `MULTIPLIER_NOT_ALLOWED` (additive `proto/v1`; future host-lobby protocol PR). The host authenticates against the lobby’s own saves (under the Proposed identity: bound to the player’s public key), rate-limits, and **locks** `multiplier` (and an instance seed) on a new instance record. The opener cannot change it after start.
2. The instance runs in-process on the host first. Players join through the portal. The instance cap is the lobby’s max players (host-set, default 50), not a separate fixed party cap of 8. The **lobby browser** lists open portals and their multipliers; if more than 5 portals are open, it shows at least the 2 lowest and the 2 highest.
3. **Multiplier is applied only by the authority** to enemy HP and damage, loot table rolls / drop quantity, XP, and farmable currency grants. The client may display the multiplier; it must not compute rewards. Gear tier rolls use the same locked value. Group HP scaling is a separate factor, below.
4. **Enemy scaling:** scale dynamically by **players in range**, using the **peak** count during an encounter. The count does not drop when players leave. **Max HP only** (integer curve); loot and other rewards stay personal and unscaled. Do not copy coefficients, range definitions, or golden values here — implement `docs/design/vision.md` **§3.5**, **§6.1 rules 5 / 6 / 6a**, and **Appendix A** in [PR #17](https://github.com/Karyu42/endless-realm/pull/17) (**pending PR #17**), and use the Appendix A golden values as tests once #17 has merged.
5. The instance is ephemeral. Persistence happens when loot/currency/XP is granted to a character (under 3a: in the host save). On crash or expiry, unlooted ground drops are gone unless we later add a short recovery window.

**Considered:** one process per instance from day one (simpler isolation, worse density); sharding the hub across workers early (not needed until a lobby or nexus is crowded); official hosted instances (deferred); a fixed party cap of 8 (to be replaced by the lobby max, pending PR #17).

## Accounts, persistence, anti-dupe, anti-cheat

**Earlier pick (accepted 2026-11-23, identity now reopened):** email + password only at first playable, hashed (Argon2id), opaque session tokens. Android would use the same account (no device-only progress that can be copied). **Considered:** Discord/Google OAuth, later — not in the first playable. No paid-cosmetics / payment surface at first playable.

**Option 3a (accepted, character ownership):** characters **live on the lobby that created them** (host save, e.g. SQLite or files) and can be imported if the other host allows it. Characters brought from elsewhere, including solo / offline ones, are **imports** and carry a `played_offline` flag. The host has a setting to allow or refuse imports — that is how “lobbies can refuse offline-played characters” is enforced. **With no official authority, a client-side flag is not tamper-proof; enforcement is the host owning its own saves.**

**Identity (Proposed — pending Karyu):** an engineering / Chief of Staff proposal is a **device-held key pair** (e.g. Ed25519) that identifies the player, with accounts **per lobby**, and the host **binding a character to that public key**. No email / password and no central account for v0.1. Karyu asked what an account service would cost and how email / password browser games handle it, so this is not decided.

**Alternative 3b (still open):** a central signing / account service that signs character saves and the `played_offline` flag, so a host can trust the flag on imports. This needs always-on official infrastructure and an ops / hosting cost (a small VM or managed auth), unlike 3a’s host-local saves, and unlike the deferred directory (Cloudflare Workers free tier, €0, ~$5/mo if outgrown).

**DB:** PostgreSQL was the earlier accepted store for accounts, characters, vault, inventory, currencies, and audit/grant logs. Redis remains optional later for sessions and presence (not required for v1). Under 3a, SQLite or files are the v0.1 host-save store. PostgreSQL remains the right store if 3b or official servers return. Docker Compose PostgreSQL is no longer needed under 3a; dropping that path is a follow-up.

**Atomic currency / vault / anti-dupe:** every item has an authority-issued id. Under official Postgres, vault deposit/withdraw, trades, and currency debits/credits run in a **single Postgres transaction** with row locks (`SELECT … FOR UPDATE`). Under 3a the same invariants apply inside the host save (one writer, idempotent grants). Loot and reward grants carry an **idempotency key** (instance id + drop id, or grant id) so a retry cannot duplicate items or currency. The client never says “give me this item”; it says “I loot entity X” and the authority decides. Disconnect mid-move must roll back or complete, never fork. Under 3a this integrity is **host-trusted**, not globally enforceable.

**Anti-cheat basics (economy integrity first):** authoritative combat and rewards; movement speed caps; input flood limits; pattern-math hit checks (swept/sub-stepped); portal-open and vault-op rate limits; append-only grant/spend log for later anomaly review. Deeper heuristic anti-cheat can wait. Under 3a the host is trusted; a determined host or a forged import can still cheat, which is the cost of no official authority.

## Hosting and local dev

**Decided:** no official servers for now. Solo runs the sim in-process with no network and no tracking. Multiplayer is a player-hosted lobby (listen server or the same export `--headless`). The host sets max player count; Karyu’s default is 50. That lobby max is the instance cap. A 1–50 hard ceiling is engineering / design, **pending PR #17** and **to be confirmed by the load test**.

**Mobile (v0.1):** Android is **join-only**. Desktop or `--headless` hosts come first and keep the default of 50. **Post-v0.1:** an Android phone listen host could default to a max of 8 players (host-side setting); that default of 8, and the listen-host ceiling, are **to be confirmed by the load test**. Phone NAT / UPnP is unreliable, so join by code or direct IP may fail on a mobile host; LAN discovery would still work on the same network. Do not rely on UPnP or a join code reaching a phone host from off-network.

**Discovery v0.1 (decided):** LAN broadcast discovery plus join by code/link or direct IP. The host tries UPnP port mapping; if that fails, the host forwards the port manually. A lobby directory (Cloudflare Workers free tier, €0, ~$5/mo if outgrown) and relay / NAT punch are deferred.

**Local dev today:** `docker compose up` (or `make dev`) still starts Postgres and the Go gameplay server and prints the Godot connect URL (`ws://localhost:…`), until follow-up host work lands. `server/` keeps building; `server-build-test` and `integration-smoke` stay required until a headless-Godot-host smoke is itself required (QA owns that switch with Chief of Staff).

**Local dev (under 3a):** run the Godot client as a listen server, or the same export `--headless`, and point other clients at `ws://` on the host’s IP (or join via LAN discovery / code). Docker Compose PostgreSQL is no longer needed under 3a; dropping or relaxing that path is a **follow-up** (do not change compose in this PR).

**CI:** client — Godot 4.7.2-stable, `godot --headless --import`, then GUT 9.7.1, and fail if tests did not actually run. Shared pattern golden fixtures run on the GDScript sim (and may still run on the Go harness). Protobuf round-trip fixtures run against the codecs. Group-scaling tests should use the Appendix A golden values from [PR #17](https://github.com/Karyu42/endless-realm/pull/17) once it merges (**pending PR #17**). **Follow-up for QA, not in this PR:** when a headless Godot host smoke exists, QA will make that check required and only then may drop `server-build-test` / `integration-smoke` from required status; the load-test gate should include the 50-bot headless host test plus a 50-player render smoke on the Android APK (join client). Do not change workflows here.

**Later (if official infrastructure is needed):** a deferred lobby directory on Cloudflare Workers as above; a relay or NAT punch; or, under 3b, a signing / account service. A small VM (Hetzner / Fly.io / equivalent) remains an option if official servers return. No Kubernetes until a single box is actually full.

**Considered:** Railway/Render for even less ops (costlier at scale); official Go or Godot dedicated servers (deferred by Karyu’s hosting decision).
